# Delete and move: what was measured, what was built

Written 2026-09-09, from the work done against [the handover](delete-and-move-handover.md) of 2026-09-08. The handover's first section is the finding that decides the design; this report assumes it has been read. Everything below was measured on this machine or pinned to a named line of source, not assumed.

## The four suspects, measured

### 1. Where the snapshot mechanism does not reach

The shadow repository's work tree is the workspace root and its `gitDir` lives in the Studio home (`src/snapshots/shadow-repo.ts`). That single fact draws the boundary, and reading the two resolvers against it draws it exactly:

- `SnapshotStore.markTouched` (`src/snapshots/store.ts`) refuses any path whose `relative(workspaceRoot, path)` escapes the root. The history cannot even *note* a path outside it, let alone restore one.
- What the workspace root actually is: `createAgentSandbox` (`src/application/studio-runtime.ts`) passes the project's first folder for a filed conversation, the conversation's own `workspace/` for a projectless one, and then *adds* write roots the shadow repo does not watch — the project's other folders (`otherFolders`), the granted scope roots, and the conversation's `scratch/`. Under a trusted policy, `resolveTrustedPath` admits any absolute path on the machine.

So: **everything the handover suspects is true, and the reaching is wider than "a granted folder".** A conversation can write to its scratch, to three other granted folders, and — trusted — anywhere, and a delete in any of those places had no recovery at all. Inside the workspace root, recovery existed and was already complete.

The boundary the tools implement is therefore not "project versus granted folder" but precisely: `isInsideRoot(sandbox.policy.workspaceRoot, resolvedPath)` — the same predicate the sandbox itself enforces (`src/sandbox/paths.ts`), so the recovery story in the tool's result and the history the shadow repository actually keeps cannot disagree. Note the one case the "project" framing hides: the conversation's own `scratch/` is *outside* the workspace root, so it falls on the trash side. That is correct, not accidental — scratch is granted in every mode and watched by no shadow repo — but it is where a reader would expect the two mechanisms to disagree.

### 2. Whether a person can reach a restore point today

**No.** Every route in `src/transport/http/routes/` was enumerated (13 files; conversations, projects, permissions, plans, providers, questions, retrieval, media, mcp, sandbox, lifecycle): no route reads or restores snapshots. No native tool wraps `SnapshotStore` — the only callers of `restore`/`list` in `src/` are `src/snapshots/` itself and its tests. In the STUDIO front-end, the `snapshot`/`restore` hits are chat-delivery snapshots and settings restore, which are different machines.

So the undo history is written on every writing turn and read by nothing. The one-paragraph version: **a restore mechanism exists and nobody can operate it.** It is also, measured while looking: never pruned — no `gc`, no `prune`, no retention anywhere — so the history grows one commit (frequently `--allow-empty`) per writing turn, indefinitely, and purge does not know the shadow repos exist either. A route, a list, and a purge story for `data/snapshots/` is the bigger next task; it is *not* this one.

### 3. Whether snapshots actually work on this machine

**They work.** Three facts, checked rather than repeated from the handover:

- The shadow repo shells out to git through `runProcess` **directly** (`shadow-repo.ts` imports `../process/exec.js`), never through `LocalSandbox.run` — so the Windows containment the handover worries about never wraps it. This is stated in `local-sandbox.ts`'s own docblock ("routing `git` through here would … take undo down with it") and the toolchain brief's failure is specifically *contained* git (an AppContainer child cannot resolve its own working directory). Different process, different failure domain.
- `resolveBinary("git")` finds the system git — 2.55.0.windows.3 on this machine's PATH. Nothing is vendored for git (`vendor/win32-x64/` holds only `rg.exe` and `studio-contain.exe`); the resolver's order for git is *system, then managed*.
- The proof is the full path through the real thing, not a mock: the new test `brings the deleted file back from the point taken before the delete` (`tests/unit/tools/filesystem.test.ts`) writes through the gate, deletes through the gate with `TurnSnapshots` wired exactly as the runtime wires it, then calls the real `SnapshotStore.restore` and gets the bytes back — real `git add`/`commit`/`restore` underneath, ~1.4 s. Had this failed, the report would have stopped here per the handover's instruction. It passed.

One incident worth a line, because it costs the next reader an hour: the undo-point **label** sequence. `TurnSnapshots` increments the counter *before* it labels (`src/snapshots/turn.ts` — the field's own docblock), so the first `beginTurn()` yields "turn 1", and the field default is *also* "turn 1" for histories that never began a turn. A test that assumes the first opened turn is "turn 2" fails; the correct sequence — and what the runtime's `prepareModelTurn` actually does — is a `beginTurn()` before the *first* tool call of the first turn. Also observed while proving this: a harness that never calls `beginTurn` at all commits every point as "turn 1" — the exact "history nobody can navigate" the docblock promises against. The runtime does call it; nothing needed fixing. It is documented here so the next label surprise costs ten minutes.

### 4. Exclusions, and what happens to a delete of an ignored file

The hard floor (`EXCLUDE_FLOOR` through the shadow repo's own `info/exclude`) and the user's `.gitignore` are honoured by the capture's `add --all -- .`. Ignored paths enter the history only through `markTouched` + `add --force`, and the force-add filters to paths that **still exist** at the next capture.

Trace the timing, because it decides the answer:

- A file the conversation *wrote* (or edited) is in `#touched` from its first write's `beforeWrite` onward; while it exists it is force-added and, once tracked, stays tracked — its later delete is recorded by the next `add --all`. **Recoverable.**
- A file that was ignored and *never touched by the agent* — anything under `node_modules/` on a project without `.gitignore`, a `.gitignore`d artefact nobody's conversation wrote: its pre-delete capture runs *before* the delete (the gate's ordering, correctly), the file is gone by the next capture, the existence filter skips it, and it was never committed. **Unrecoverable, even inside the project.** The delete's result message does not hedge about this; it describes the mechanism that applies, and this case is the known residue of that mechanism.

The gate's ordering — capture, *then* `markTouched` — is deliberate (`turn.ts`'s comment) and was not reordered. The consequence is only the ignored-file case above.

## What was built

`native/delete` and `native/move`, registered in the filesystem family (`src/tools/filesystem/`), sharing its access log, declaring `effects: ["write"]` — and thereby earning their restore point from the gate by the effect table, with the gate untouched and the contract's order (capture → markTouched → execute) preserved. `native/mkdir` was **not** built; see the end.

- **`delete`** — a file needs the read-before-modify rule (the `write` precedent: the conversation wrote it or read it, so it knows what it is discarding — the handover's reasoning, enforced); a directory needs **a different precondition, not a stronger one**: a directory cannot be read (`read` refuses one), so read-before-modify cannot apply, and read-every-contents is unenforceable at the scale recursive delete exists for (`node_modules`). What *can* be enforced is explicitness: `recursive: true` in the call is the acknowledgment, and the recovery note in the result is the safety.
  - Inside the workspace root: `LocalSandbox.remove` — its workspace-root refusal and `resolveWrite` resolution untouched, as required.
  - Outside it: the path is **moved, not destroyed** — see the trash. No path is covered by both mechanisms: inside, the file is removed and the snapshot history is the recovery; outside, the trash is the *only* recovery. The predicate is one comparison, shared by the message and by the history's actual reach.
  - The result says which recovery applied, because "this is recoverable and here is how" is part of the answer after a delete nobody expected.
- **`move`** — both endpoints resolve through `resolveWrite` and are each authorized (the gate's `resources`); the *source* is what the gate snapshots. A taken destination is refused unless `overwrite: true`; overwrite requires the casualty to have been read (the read-first rule, at the one place a move discards anything); a directory is never wholesale-replaced by overwrite (that is `delete`'s work); a directory cannot be moved into itself; the workspace root is refused at either end by `LocalSandbox.rename` — the removal-side refusal, mirrored for the renaming side. Missing destination parents are created silently and *reported*, by the same `directoriesToCreate` `write` uses (now exported — one copy of the meaning, per this codebase's oldest lesson). The access log records the old path as absence and deliberately does *not* record the destination: the conversation moved the file without seeing what it contains, and the log only speaks for what was seen, so the next edit reads first.
- **The trash** — `conversationTrashDirectory` in `platform/paths.ts`, beside the other conversation accessors, in the `data/` category (losing it loses the only copy). Layout: one directory per delete — `<ISO timestamp>/content` + `origin.json` recording the original path, the original name, the time, and the conversation. The name is for people; `origin.json` is for anything that reads. Same volume: a rename, O(1) at any size. Across volumes: copy-then-remove, so the original survives every failure, and a failed move cleans its partial entry and reports — never "silently sometimes works". No size cap: a too-large delete is a *reported* failure, not a policy. Directory: `src/tools/filesystem/trash.ts`; the sandbox is deliberately not involved (the target was resolved and authorized through `resolveWrite`; the destination is harness state no policy root names — the reasoning is in the module's docblock).
- **The Windows Recycle Bin: no, and the handover's expectation holds, for its second reason rather than its first.** Reaching it means `SHFileOperation`/`IFileOperation` — COM — which from Node means a native module or a spawned helper. A spawned helper *is* permitted here (the trash and the snapshots run from the harness process, which already spawns git; the AppContainer's restrictions govern its *children*, not it) — so the handover's process-argument, while true of the children, is not the deciding one. The deciding reasons are the ones independent of process: the Bin is per-user and per-volume, so a file on a second drive or a UNC path may not go there at all — a mechanism that silently sometimes works is worse than one that never claims to — and the dependency weight (this repo ships exactly two vendored binaries and prized its minimal dependency list) buys nothing this trash does not. Sixty lines of `fs.rename`/`cp` behave identically for every path `resolveWrite` will ever admit.
- **Retention.** The trash lives *inside the conversation's own directory*, so it dies with the conversation: `conversations/purge.ts`'s `removeTree` already removes the whole tree, best-effort, last of all. Its doctrine — permanent destruction is exactly one thing, deleting a conversation; nothing sweeps, nothing expires — therefore extends to the trash unchanged, and **purge.ts need not know the trash exists.** It does not. Verified by `purge.test.ts` passing untouched.
- **The system prompt** gained entries for both tools (`src/context/system-prompt.ts`) — the inventory test (`system-prompt-tools.test.ts`) scans the source for every `native` capability and requires the prompt's list to account for it, which is exactly why this was not forgotten.

## What must not break — and did not

- **The snapshot contract.** The gate's ordering is untouched; the new tools earn their undo point by declaring `write` and nothing else. Measured: the delete→restore test runs the real mechanism through the real gate.
- **`resolveWrite` as the only path resolution.** Both tools resolve every path they touch through it; the trash's destination is the one deliberate exception (harness state, not an agent-named path), argued in `trash.ts`'s docblock.
- **The workspace-root refusal.** Present in `remove` (unchanged) and now mirrored in `rename` for both endpoints. Tested from the tool and from the sandbox.
- **The access log.** Delete records the deleted path's absence; move records the source's absence and no more. Tests: the record exists, the destination's does not, and a file recreated at a deleted path forces a fresh read — "changed after it was read", because the conversation's last word on that path was the deletion.

## Verification

`pnpm test` from STUDIO HARNESS, one suite at a time, fresh build. Final numbers: **1868 passed, 25 skipped, 0 failed** (1893 total). The handover's baseline (1835 passing, 25 skipped) describes a suite 33 tests smaller than the one measured here — 21 of the difference are this work's, the rest arrived between the handover's 2026-09-08 writing and this measurement; the invariant that matters, 0 failing, holds. The 21 new tests cover, at the handover's minimum and past it: the real delete→snapshot→restore; the workspace-root refusal (both tools, from the tool and the primitive); a clobbering move refused, and the overwrite granted only to a conversation that read the casualty; the access log recording both tools; the outside-root trash move with its `origin.json` recovery record; read-before-delete; the recursive flag; the dir-into-itself and wholesale-replacement refusals; the missing-parents report; and the returned-fresh-read after a delete. `pnpm typecheck` and `pnpm lint` are clean — two incidental findings fixed en route: four unnecessary type assertions of this work's own, and one pre-existing literal `0x08` control character in `environment-block.test.ts`'s regex, now written as the `\b` escape, exactly as that repository's own doctrine (`access-log.ts`'s separator note) prescribes.

## What this work deliberately did not do

- **No restore surface.** The bigger finding stands: the history is written and unread. The next task, in priority order: a route (list + restore) on the project the way `orphan-trees` is routed today; then a retention story for `data/snapshots/` (it grows a commit per writing turn and nothing prunes it — purge does not know it exists).
- **No `mkdir`.** `write` creates every missing parent (`sandbox.writeFile`'s `mkdir`, reported by the write), and `move`'s rename does the same through `LocalSandbox.rename`. A separate tool buys only the *empty directory* — which almost nothing needs — and costs its schema tokens in the cached prefix of every conversation, which is the same economics that already killed `list` (glob covers it; see the filesystem index's docblock, where both are now written down).
