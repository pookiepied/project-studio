# Independent audit — 2026-08-15

An independent audit of `STUDIO HARNESS/` (the product), `STUDIO/` (the
client), and `documentation/`, run from the prompt in
`documentation/work/independent-audit-prompt.md`. Everything below was
established by reading code, running the suite, and tracing callers — not by
trusting documents.

---

## 1. Baseline

Run before any other investigation, from `STUDIO HARNESS/`:

| Typecheck | `pnpm typecheck` | clean (`tsc --noEmit`, 0 errors) |

### The 2 skipped tests

Both are in `tests/integration/credential-keyring.test.ts:31,76`. They are
`describe.skipIf(!available)` / `describe.skipIf(available)` around the real

machine the store **is** available, so the six real tests ran and only the
"store unavailable" branch skipped. **The skip claim is legitimate** — it is an
environment fact, not a hidden gap, and the opposite branch has its own test.

## 2. Method

### What I examined

- **All 38 ADRs** (`documentation/decisions/0001–0038`), each Decision section
  traced to code.
- **~60 of 159 `src/` files read in full**, covering every security-relevant
  module: permission kernel/grant store/trust/policy/mode/scopes, the effect
  table, the gate/bounds, snapshots (shadow repo, store, turn), process exec,
  vendor resolver, net (destination, http, own-ports), admission
  (verifier/credential/context/scopes), harness launcher/readiness, auth
  (login, google-login, session-token-provider), credentials
  (keyring/credential-store), the full MCP stack (registry, supervisor,
  connection, capabilities, input-security, management, channels), retrieval
  (service, slots, settings, http, errors, registry), models (bootstrap,
  provider-config, studio-cloud client/event-mapper/sse-parser/access-token,
  local runtime/credential-bridge/config), observability (index, config,
  error-reporter, redaction, redaction-rules), execution (context, outcomes),
  identity/uuid, platform paths, storage (database, migrations), transport
  (create-app, routes, middleware), tools (git argv/classify/index, shell
  index/resolve, filesystem read/write/edit, native index, types), and the
  composition root (`app.ts`, `agents/studio.ts`, `studio-runtime.ts`,
  `harness-client.ts`).
- **Every route registration** in the harness, traced through
  `create-app.ts` mounting order, plus the Flue generated routes (verified
  against the compiled `dist/` bundle).
- **Every SQL statement** in `src/`, mapped to the 9 migrated tables.
- **Every environment variable** read in `src/` and in the patched Flue
  entrypoint, cross-checked against `.env.example` and the ADRs.
- **Every TODO/FIXME/deferral marker** across `src/`, `tests/`, `STUDIO/`, and
  `documentation/`.
- **All 73 test files** by name and structure; the 2 skips examined in detail;
  the `toBeDefined()`/`skip`/`only` surface swept.
- The desktop caller (`STUDIO/src-tauri` supervisor, `STUDIO/src/platform/
  harness/*`, `useFlueChatSession.ts`) to verify the ADR 0028 claim.
- The phase ledger, the task-008 completion doc, and — last — the remediation
  register.

### What I did not examine

- `STUDIO Gateway/` — retired by explicit instruction.
- ~60% of `src/` files were not read in full, mainly the retrieval provider
  adapters (tavily/brave/exa/jina/firecrawl), the wire-layer files
  (framing/jsonrpc/pending/backoff/lifecycle/definition-hash/era/handshake),
  the local model `apis.ts`/`catalog.ts`/`provider-service.ts`, the studio-cloud
  `request-mapper.ts`/`stream-events.ts`/`catalog.ts`/`errors.ts`, and the
  remaining filesystem/search/web tool internals. These were covered by their
  tests and by the modules that consume them; I did not find a claim attached
  to them that I could not verify through a consumer.
- The full Flue dependency internals; where Flue behaviour mattered (routes,
  idempotency patch, agent initializer identity) I verified through the patched
  entrypoint, the compiled bundle, and integration tests rather than reading
  the dependency wholesale.
- `node_modules` and `dist/` as source of truth (used only to confirm the
  bundle matches `src/` composition).

I ran the full suite once (it matches baseline) and targeted greps throughout.
I did not delete code or run mutation experiments; findings below that cite
"mutation-verified" are quoting the project's own register, not new work.

## 3. Findings

Ordered by severity. The striking overall result: **this codebase is far more
honest than the audit prompt prepared me to expect.** Almost every claim I
checked — including the security-critical ones — has real code behind it, and
the remediation register is candid about what remains open. The findings below
are mostly documentation lags and small dead code, not false security claims.

### High

#### H-1. `api-inventory.md` documents grant/trust routes that do not exist

- **Location:** `documentation/architecture/api-inventory.md:25-26`
  (documented), vs `STUDIO HARNESS/src/transport/http/routes/permissions.ts`
  (only `/pending` routes exist).
- **The claim it contradicts:** the inventory lists
  `GET /api/permissions/grants` → `PermissionGrant[]` and
  `DELETE /api/permissions/grants/:id` → `204`. The route module registers
  exactly three routes: `GET/POST/DELETE /pending...` (`permissions.ts:44-75`).
  A grep for `grants` in `src/transport/http/routes/` returns nothing.
- **How it fails:** a client following the inventory would get `404` on
  `GET /api/permissions/grants`. The grant *store* methods exist
  (`grant-store.ts:225 list()`, `:248 revoke()`) but have **no caller in
  `src/`** — grants are written by the kernel and consulted by it, but nothing
  can list or revoke them.
- **How I verified it:** read the route module; grepped for `grants` across
  `src/transport/http/routes/`; confirmed no other route file registers them;
  confirmed `PermissionGrantStore.list/revoke/revokeConversation` have no
  production caller.
- **Confidence:** Confirmed.
- **Note:** the register already tracks this as **#39** ("api-inventory.md:3
  says 3/5 Done; task 008 says 5/5") and **#49** (008.9 grants/approval API —
  open, with the checklist items still `[ ]`). So this is **known**, and the
  inventory's status line ("3/5 Done") is the specific understatement: the two
  open items are exactly these missing routes.

#### H-2. `api-inventory.md` promises an API version header that does not exist

- **Location:** `documentation/architecture/api-inventory.md:34` — "Version
  header: `X-Project-Studio-API-Version: 1` (integer). Client sends `1`,
  server echoes `1`…"
- **The claim it contradicts:** `src/transport/http/create-app.ts` and the
  admission middleware (`middleware/admission.ts`) contain no version-header
  logic — no read, no echo, no `410 Gone` path.
- **How it fails:** the documented compatibility contract is not implemented;
  a client that sends the header gets it silently ignored, and the "410 when
  unsupported" behaviour cannot occur.
- **How I verified it:** read `create-app.ts` and `middleware/admission.ts` in
  full; grepped for `API-Version` across `src/` and the patch — no match.
- **Confidence:** Confirmed.
- **Note:** tracked as **#40** ("promises an `X-Project-Studio-API-Version: 1`
  header. `create-app.ts` has no such logic. Implement or stop documenting.").
  Known.

#### H-3. `api-inventory.md` cites `src/application/ports.ts`, which was deleted

  owner column cites `McpManagementPort` at `src/application/ports.ts`).
- **The claim it contradicts:** the file does not exist. The register records

- **How it fails:** a reader tracing the documented owner reaches a nonexistent

- **How I verified it:** globbed `src/**/ports.ts` — no match; read
  `mcp-management.ts` and `create-app.ts`.
- **Confidence:** Confirmed.
- **Note:** this is the same class as #39/#42 (task-008 statuses) but is not
  itself listed in the register; the register records the *deletion*, not the

#### H-4. ADR 0033 is marked "proposed", but the core is implemented

- **Location:** `documentation/decisions/0033-execution-identity-and-operation-correlation.md:3` — "Status: proposed; Task 008.44 gate".
- **The claim it contradicts:** `src/execution/context.ts` fully implements the
  typed `ExecutionContext` (requestId/operationId/parentOperationId/attemptId/
  kind/clientId/sessionId/flue links), and it is **wired**: the admission
  middleware creates a root context per request (`middleware/admission.ts:42-49`),
  `observability/flue.ts` links Flue operation ids at turn boundaries, and the
  structured logger consumes it. The "008.44" gate reference is also stale —
  008.44 was renumbered to 008.4 (per `archive/phase-11-mcp/008-phase-1-11-completion.md:80`).
- **How it fails:** a reader treats ADR 0033 as not-yet-decided and re-litigates
  an implemented design, or misses that the *durable projection* and
  `createRetryExecutionContext` production caller (items 4-5 of the ADR's own
  implementation order) genuinely are not done.
- **How I verified it:** read `execution/context.ts`, `middleware/admission.ts`,
  `observability/flue.ts`; confirmed `createRetryExecutionContext` has a test
  and no production caller (marked declared-not-wired at source, matching the
  register's #31 reclassification).
- **Confidence:** Confirmed.
- **Note:** the register's #31 explicitly reclassified the retry/context
  exports as deliberate. The stale **status line** is the new part.

#### M-4. `durableDirectories()` exists to derive the backup set, and nothing calls it

- **Location:** `STUDIO HARNESS/src/platform/paths.ts:162-164`.
- **The claim it contradicts:** ADR 0014:68-70 — "`durableDirectories()`
  derives the backup set from the same accessors everything else uses, so a new
  durable directory cannot be added and then forgotten by the backup." The
  function is the **entire** enforcement mechanism for that claim, and it has
  no caller in `src/` (only its own test, `tests/unit/platform-paths.test.ts`).
  A backup tool that never calls it gets no protection.
- **How it fails:** the "cannot be forgotten" property depends on something
  actually consuming the list; nothing does. The function itself is correct
  and returns `config/` + `data/`.
- **How I verified it:** grepped `durableDirectories` across `src/` — defined
  at paths.ts:162, used nowhere.
- **Confidence:** Confirmed.
- **Note:** ADR 0010's backup/export/sync deferral is recorded as open in the
  register; this is the *unrecorded* part — the helper built to serve a backup
  that has no consumer. **New.**

#### M-6. The `#turnSnapshots` map grows without bound, and the code says so

- **Location:** `STUDIO HARNESS/src/application/studio-runtime.ts:261`
  (`readonly #turnSnapshots = new Map<string, TurnSnapshots>()`), `:372-380`
  (keyed by `projectId\0conversationId`, never evicted).
- **The claim it contradicts:** the audit's own product-class requirement —
  bounded growth of in-memory maps. The code comment at `:385-390` admits it:
  "Still grows with distinct conversations, which is bounded only by how many a
  process sees… this map needs an eviction policy and #68 is where that is
  decided."
- **How it fails:** a long-lived harness process that serves many distinct
  conversation ids accumulates one `TurnSnapshots` (each holding a
  `SnapshotStore`, a git repository handle, and a touched-set) per conversation,

- **How I verified it:** read the runtime; no `delete` on the map exists.
- **Confidence:** Confirmed.
- **Note:** the register's **#35/#67** covered the *unkeyed Set* version; the
  keyed Map is the **fix**, and its growth note refers to the now-withdrawn

  tracked**. **New.**

## 4. Silent omissions

Category 6 — things that should exist and were never discussed. I enumerated
and checked the five derivable surfaces; the sixth method (product-class
requirements) is where the real findings live.

### What I enumerated and found complete

- **ADR decisions → implementation.** All 38 ADRs traced. The load-bearing
  ones (0007 keychain, 0012 kernel, 0013 substrate, 0015 scope ladder, 0016
  undo, 0017 bounds, 0018 trust/modes, 0019 shell, 0020 effect table, 0022
  network destination, 0023 retrieval slots, 0024 capability list, 0025
  provenance, 0026 redirects, 0027 failed-POST, 0028 admission, 0030 identity,
  0032 recovery, 0035 ports, 0036 durable decisions, 0037 observability, 0038
  agent grants) each have real, cited implementations. The ones marked
  deferred (0003 optimizer, 0014 directories, 0016 retention, 0019 T-13, 0023
  C-13, 0033 projection) are honestly marked, and the code matches the marking.
  **No ADR with a "deferred" marker hides an implementation, and no accepted
  ADR I checked was missing its implementation.**
- **Type unions / enums / schema variants → producers and consumers.** The
  four effects, five admission scopes, four client types, three grant
  durations, three execution modes, seven retrieval error kinds, three
  credential scopes — every member has a producer and consumer. The one
  deliberate exception is `CapabilityOrigin`'s `"skill"` member (Phase 12) and
  `ExecutionOperationKind`'s future kinds (`"skill"`, `"subagent"`,
  `"workflow"`), both of which are declared for later phases with the code
  paths marked; these match the phase plan and are not silent.
- **DB tables → readers/writers.** All 9 tables used; no orphan SQL; the only
  write-only table is `schema_migration` (M-3).
- **Routes → inventory.** Every route exists in code; every documented route
  either exists or is the known-open #39/#40 pair (H-1, H-2). No route exists
  without admission; no route is reachable unauthenticated (verified by
  mounting order and the compiled bundle).
- **Env vars → documentation/validation.** 41 variables enumerated. All
  `.env.example` entries are read somewhere except `GOOGLE_DESKTOP_CLIENT_ID`,
  which belongs to the separate auth worker (documented as such — not a
  defect). The undocumented-but-read set (`PROJECT_STUDIO_ADMISSION_*`,
  `PROJECT_STUDIO_HOME`, `PROJECT_STUDIO_VENDOR_DIR`, the two Google URL
  overrides) are dev/launcher plumbing, deliberately absent from `.env.example`
  (the admission ones by design — they are per-launch secrets). Validation is
  strict where it matters (URLs, timeouts, booleans, provider config) and
  deliberately lenient where the docs say it is (capability switches,
  redaction rules).

### What a product of this class must have — and where it lives

| Requirement | Where it lives | Verdict |
|---|---|---|
| Cancellation and timeouts on every long operation | `tools/bounds.ts` (deadline + abort + FIFO queue), `process/exec.ts` (timeout, abort, output limit, tree kill), `net/http.ts` (deadline, max bytes, max redirects), MCP request timeout | **Present** |
| Crash recovery | Flue durable submission journal; ADR 0032; `tests/integration/harness.test.ts` (clean restart + SIGKILL recovery) | **Present** |
| Concurrency limits | `CallBounds` default 8, FIFO, aborted-waiter removal | **Present** |
| Bounded growth of accumulators | stdout/stderr capped (8 MiB / 200 lines); `#pending` maps cleaned on settle; **exception: `#turnSnapshots` (M-6)** | **One gap** |
| Secret redaction on every output path | always-on redaction rules + sensitive-field dropping; error contract never serializes cause/stack; `safeSerializeValue` on every log path | **Present** |
| Child-process cleanup on every exit path | `killProcessTree` (`/T /F` on Windows, process-group kill on POSIX); `stop()` awaits children; launcher kills on timeout; **exception: the shipped Tauri supervisor inherits the full environment (the `// For now` at `supervisor.rs:197`) — an open deferral, recorded in code, not tracked in the register** | **One open item** |
| Migration path for existing user data | append-only migrations, refuse-higher-version, per-migration transactions, secret-column guard on every open | **Present** |
| Audit-ability of what the agent did | Flue canonical transcript; `CallGate.inFlight`; error reporter (log + span + counter); execution context correlation; **exception: grants are not listable/revocable through any API (H-1)** | **One gap** |

The two real silent omissions I found are therefore: **M-6** (unbounded
`#turnSnapshots` map — the code itself flags it, but nothing tracks it) and
**the Tauri supervisor's unfiltered environment** (`supervisor.rs:197`, "For
now inherit all except credential") — which is exactly the kind of "for now"
the audit is meant to surface, and which is **not** in the register. Both are
genuinely new.

## 5. Unverified

- **The `#turnSnapshots` eviction need at scale.** I confirmed the map never
  evicts. I did not measure a real long-lived session count, so the *impact*
  (memory per conversation, git-repo handle cost) is reasoned, not measured.
  Verification would need a long-running harness serving many conversations
  with a heap snapshot.
- **The retrieval provider adapters' wire behaviour** (tavily/brave/exa/jina/
  firecrawl). Their tests pass and the shared `callProvider`/mapping layer is
  read; I did not read each adapter's request/response parsing in full.
- **The `dist/server.mjs` patch and the compiled Flue route surface.** I
  verified the route list through the compiled bundle and the patch hunks as
  the background agent reported, and read the launcher's use of the patch
  contract, but I did not re-derive every Flue route from the dependency's
  source. If Flue adds a route in a future version, the admission coverage
  would need re-verification (the current `create-app.ts` ordering covers
  everything mounted today).
- **Linux/macOS behaviour.** Nothing here runs on those platforms; every
  cross-platform claim (process groups, `taskkill`, PATH blanking, keyring
  availability, path case sensitivity) is a Windows measurement plus an
  inference — exactly as the prompt predicted. The code is written *defensively*
  about this (the Windows-specific comments are unusually explicit about what
  was measured), but the inference stands unverified on the other platforms.
  The one place I would bet the inference is wrong: `resolveBinary`/`resolveProgram`
  reading the host `PATH` to *locate* programs — on Linux this is fine, but the
  code's own argument ("locating is not passing") depends on `runProcess`
  never forwarding PATH, which is enforced only by the `environment.PATH = ""`
  line in `buildEnvironment`. That line is tested, but the whole chain is
  Windows-verified only.
