## 1. Locked decisions

These are settled. Do not re-litigate them mid-implementation.

### Design (full detail in DOC §11–§12)
1. **Pure-neutral monochrome. No accent colors — ever.** No blue/red/green/sage/amber/purple. White + light grays (light mode), graphite (dark mode).
2. **Primary text is pure black** (`#000` light / soft white `#F2F2F2` dark). Black is for ink and rare high-contrast elements only — never for surfaces/fills/borders.
3. **Temperature:** essentially neutral, faintest cool undertone in light, neutral graphite in dark. Never a perceptible color.
4. **State lives on separate channels** (DOC §11.1): hover = quietest fill only; selected/active = stronger fill **+ pure-black text + medium weight + optional 2px marker**; focus = neutral ring; hover-on-selected never stacks a third shade. This is the fix for the hover/selected adjacency competition.
5. **Elevation is asymmetric** (DOC §11.2): light mode = hairline border + soft shadow; dark mode = lighter graphite fill, minimal shadow.
6. **Status without color** (DOC §11.3): success/error/warning via icon + weight + neutral surface. Destructive = filled graphite/near-black + icon, **not red**.

### Architecture
7. **Feature-based organization is the target** (DOC §14, refined here in §2). Everything for a feature lives together. This is decided — not deferred, not optional.
8. **Routing stays as the current `switch`/`useState`.** No router migration. We only delete the *vestigial* router artifacts (`ProtectedRoute`, the dead `/oauth/callback` check). Revisit a real router only as an optional post-project item.
9. **Path alias `@/*`** is introduced first and used for all new/edited imports.
10. **Both build targets must stay green:** `vite.config.ts` (Tauri desktop) **and** `vite.config.web.ts` (web). Every phase verifies both.

### Still-open (do not block early phases; resolve before the phase that needs them)
- **Micro-typography** (DOC §25.4): are 9–11px sizes intentional density → formalize `2xs/3xs`, or drift → raise to 11px floor? *Needed by Phase 1.*
- **Brand-logo exception** (DOC §25.5): confirm multi-color external brand logos (Gmail/Google/Claude) may keep their brand color. *Needed by Phase 3.*
- **Dead-code deletion** (DOC §25.8): confirm `ChibiAvatar`, `ComingSoon`, `ProtectedRoute` removable; keep `SplashPreviewPage` (dev-only). *Needed by Phase 6.*
- **Out-of-scope subtrees** (DOC §25.9): `src/agent/`, `src/ai/formatter/`, `src/assets/` — follow-up audit? *Not blocking.*

### Placement rules (decision tree for "where does this go?")
1. **Used by 2+ features and has no product logic?** → `components/ui` (visual primitive), `components/layout`, `components/feedback`, or `components/overlays`.
2. **Belongs to exactly one feature?** → that `features/<x>/` folder, in the right subfolder (`components`/`hooks`/`services`/`context`).
3. **Pure function, no JSX?** → `utils/`. **Has JSX?** → it's a component, not a util.
4. **App-wide constant?** → `constants/`. **Feature-only constant?** → `features/<x>/constants.ts`.
5. **Global app state (auth/settings/nav/offline)?** → `contexts/`. **Feature state?** → `features/<x>/context/`.
6. **Infra (network/storage/errors/logging/platform)?** → `services/`. **Feature business logic?** → `features/<x>/services/`.

## 3. Execution strategy

### 3.1 Touch-once, feature-by-feature (the anti-rework rule)
The user's concern — "don't implement, then move, then fix imports = double work" — is the central design constraint of this plan. Mitigations, in order of impact:
1. **Foundations are structure-neutral.** Tokens (`tokens/`, `styles/`, `tailwind.config.js`) and generic primitives (`components/ui`) live in their final home from the start. Building them moves nothing.
2. **New files are born final.** Any file we create lands directly in its target location (§2). We never create-then-move.
3. **Per-feature, move + refactor together.** In Phase 4, when we open a feature we *both* relocate its files into `features/<x>/` *and* do its design-system work (adopt primitives, tokenize colors, fix states/a11y/icons) in the same pass. Each file is edited once.
4. **Alias-first.** With `@/*` in place, relocating a file means updating its own imports + the references to it — overwhelmingly handled by IDE "move file" / find-replace, not hand-editing.

### 3.2 Sequencing principles
- **Foundations before features.** Phases 0–3 (alias, scaffold, tokens, primitives, layout/icons) must be complete and proven before any feature migration. This is why feature reorg is *not* risky here — the system it depends on already works.
- **Smallest, lowest-risk feature first.** Phase 4 order runs simple → complex so the migration recipe is proven on cheap features before the god-objects (`WorkspacePage` 981, `ChatProvider` 1355).
- **One feature per working unit, independently verifiable.** Each migrated feature must build (both targets) and look correct before we start the next.
- **Cleanup last.** Shared-layer consolidation and dead-code removal happen only after features are settled, so we're not deleting/moving things still in flux.

### 3.3 The per-feature migration recipe (reused for every Phase 4 feature)
For feature `<X>`:
1. Create `features/<X>/` with its subfolders; move its files in (update imports via tooling).
2. Move feature-scoped hooks/contexts/services/constants/types in alongside.
3. Replace raw elements with primitives (`<button>`→`Button`/`IconButton`, raw inputs→`Input`/`Textarea`, hand-rolled modals→`Modal`, ad-hoc spinners→`Spinner`, etc.).
4. Replace hardcoded colors / `gray-*` / `dark:*` pairs with semantic tokens; apply the §11.1 state model.
5. Replace ad-hoc icons with the semantic icon barrel; fix sizes/weights.
6. Replace arbitrary `text-[Npx]` / `rounded-[..]` / `duration-[..]` with scale tokens.
7. Add a11y where the primitive doesn't already provide it (aria-labels on icon buttons, etc.).
8. Verify (§4). Tick the feature's tasks.

## 4. Verification & quality gates

Run these at the end of every task that changes code, **and** as the **mandatory dedicated verification
pass** at the end of every phase / migrated feature. The end-of-phase pass is a *separate step from
implementation* and is **non-optional** — it cross-checks the work against the **actual codebase, not
just these docs** (see `00-INTENT.md` §5 for the full process and §6 for completion criteria). If it
finds anything, fix it and re-verify **before** the phase is marked `☑`. Record the outcome in `04`
(and any finding in `03`).

**Standing gates (every phase):**
- **Typecheck:** `tsc` clean (the build runs `tsc && vite build`). `noUnusedLocals`/`noUnusedParameters` are on — moves must not leave dangling imports.
- **Both builds compile:** run from `STUDIO/` — `npm run build` (desktop, `vite.config.ts`) **and** `npm run web:build` (web, `vite.config.web.ts`). A change that only passes one is not done.
- **Cross-check against the code, not the prose:** grep/inspect the real files to confirm the docs' claims are true and wired in. For the phase's *shape*, check the failure modes it could introduce — e.g. new token/utility names that **collide with or newly-activate** existing classes; deletions that aren't actually unreferenced; centralized definitions that left a **duplicate source**; CSS **specificity/precedence** edge cases and element-vs-decoration side effects.
- **Visual check (light + dark):** the touched surface renders correctly in **light and dark**, and at a narrow width if layout changed. If the surface is unreachable (e.g. auth-gated), verify the substance directly (runtime computed token/utility values) and say so in `04`.
- **State-model check:** for any list/menu/nav touched — hover, selected, hover-on-selected, and focus are all visually distinct per DOC §11.1 (this is the headline design goal; check it explicitly).
- **A11y spot-check:** keyboard focus ring visible; icon-only controls have `aria-label`; modals trap focus + close on Esc; reduced-motion honored (Phase 1 landed the global rules).
- **No regressions:** the feature still behaves exactly as before (this is a restyle/reorg, not a behavior change).
