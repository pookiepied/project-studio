# ADR 0015: How Wide An Approval Is

Status: Accepted

## Context

The permission kernel matches on resources, so `git:log` and `git:push` are
decided separately and a grant can be narrowed to `src/**`. All of that
machinery works and is tested.

Nothing used it. `PermissionApprover` could return a `resourcePattern`, and when
it returned none the kernel stored the call's exact resource. Since no approver
existed yet, every standing approval was per-resource: "always allow" meant
"always allow this one file", and a working session would accumulate one grant
per file touched. That was recorded as `T-01`.

The narrow default was right and is kept. The failure it prevents — a dialog
that displays one file and silently authorizes a directory — is far worse than
being asked twice. But left alone it produces approval fatigue, and a permission
system that trains users to click through it has stopped being a permission
system.

So the question is not whether to offer wider approvals. It is **who composes
them**, and that has to be settled before a UI exists, because the UI is exactly
the wrong place to settle it.

## Decision

### The kernel offers; the approver selects; the kernel resolves

`PermissionRequest` now carries `scopes`, a short list of `PermissionScope`
options generated by the kernel from the resolved resource. The approver answers
with a `scopeId` — one of the ids it was given — and the kernel maps it back to
a pattern.

`resourcePattern` is gone from the approver's answer. An approver cannot author
a pattern, so no dialog can grant something wider than what it displayed. This
is the substance of the decision: it makes the safety property structural rather
than conventional. A convention holds until someone builds a screen without
having read this file.

It also means every surface — the React app, a CLI, a test double, an MCP-driven
approver later — gets the same ladder without reimplementing it, and none of them
can drift.

### Users are never asked to write a pattern

Corollary, and the reason the ladder exists at all. A glob typed into a modal,
under time pressure, with an agent waiting, is a decision made badly: the
reliable way to make the dialog stop is to type something too wide. Labels shown
to the user contain no glob syntax at all, and a test asserts it.

Authoring arbitrary rules is a real need and belongs in settings — read in full,
revisable, away from a blocked task.

### Breadth and duration stay independent

`scopeId` (what is covered) and `GrantDuration` (how long) are separate fields.
Collapsing them into one list of options would produce a six-item dialog and
would drop combinations people actually want, "this whole folder, but only for
now" being the obvious one.

### The path ladder is capped at the workspace

For a filesystem path: **this file → this folder → this project**, narrowest
first, so a hurried click lands on the safest option.

Nothing above the workspace root is ever offered. That rung would let one click
authorize the user's home directory, and there is no honest way to phrase it in a
dialog. Rungs that resolve to the same set are collapsed, because a question with
one real answer wastes the user's attention on the occasion we most need it.

### The command ladder has one rung

For a command resource: **this command**, and nothing wider.

The obvious second rung is `git:*`, and it is precisely what must not be one
click away. It contains `push`, `reset`, and `clean`, so a user approving a
`git status` would be authorizing history rewrites. Approving a whole family is
legitimate and belongs in settings, where it is read deliberately.

### An unoffered answer narrows, and is reported

An approver returning an id we did not offer gets the narrowest scope, and the
kernel reports it through `ErrorReporter`.

Failing the call would turn a UI bug into a broken product; honouring the answer
would turn it into a security hole. Narrowing makes a broken approver merely
repetitive, and reporting means it surfaces as prompting-with-a-cause rather than
as a mystery.

## Consequences

**Good.** `T-01` is closed in the backend. When the approval UI arrives it
renders `request.scopes` and returns an id — there is no permission logic in the
UI to get wrong, and no pattern syntax in it at all. A session in which the user
picks "this folder" once now touches every file under it without asking again.

**Costs.** The ladders are fixed in code, so a new resource kind needs a ladder
written for it rather than configured. That is deliberate at this size: a
configurable ladder is a pattern language with a second author, which is the
thing this ADR exists to prevent.

Only a chosen scope is ever stored, so widening later means approving again at
the wider scope. Acceptable, and arguably correct — the wider grant should be a
decision the user made, not one inferred from repetition.

**Left open.** Whether a standing grant should expire. A permanent `src/**`
grant is a different risk from a session-long one, comparable products differ,
and there is no recommendation worth defending yet. `GrantDuration` already has
the three values needed to add expiry without a schema change.
